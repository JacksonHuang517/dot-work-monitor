# Monitor authorization service

Node 22.14 OAuth authorization server and streaming MCP front proxy. It uses `oidc-provider`, Express and JOSE with pinned package versions. This package is MIT licensed; third-party dependencies retain their own licenses. No credentials are included.

`npm ci`, `npm run typecheck`, `npm run build`, and `npm test` install and verify the package. `npm start` runs `dist/main.js`. Settings come from the process environment; `.env` files are not loaded automatically.

## Configuration

Copy `.env.example` and fill `PUBLIC_ORIGIN`, `FEISHU_APP_ID`, `OWNER_OPEN_ID` and `FEISHU_TENANT_KEY` from your own account/application. Every field is required and empty values fail closed. `PUBLIC_ORIGIN` must be a bare HTTPS origin. `OWNER_DISPLAY_NAME` defaults to `Owner`. Identity matching requires the exact application, tenant and owner Open ID.

Required protected absolute files: `FEISHU_APP_SECRET_FILE` (application secret), `INTERNAL_KEY_FILE` (at least 32 bytes, shared with the Python service), `OAUTH_JWKS_FILE` (private RS256 JWKS JSON), `COOKIE_KEYS_FILE` (JSON array of keys of at least 32 bytes) and `AUTH_DB_KEY_FILE` (base64 of a random 32-byte database key). Files must not be accessible by group or others. `AUTH_DATABASE_PATH` is required and absolute. Runtime secret files conventionally reside under `/run/monitor-secrets`; provision them using your deployment's secret manager. Never commit them. `node dist/generate-keys.js /absolute/protected/directory` generates JWKS, cookie keys and a database key, without overwriting existing files. It does not generate an app secret or the shared internal key.

`AUTH_HOST=127.0.0.1`, `AUTH_PORT=8560` and `AUTH_TRUST_PROXY=loopback` are defaults. A container deployment may use `AUTH_HOST=0.0.0.0` and `AUTH_TRUST_PROXY=1` only when the listener is reachable exclusively through the trusted ingress, which must overwrite forwarded headers. The MCP backend is `127.0.0.1:8561` and must require the shared internal key and enforce trusted scope headers. Optional `OAUTH_CLIENT_ID` and JSON `OAUTH_REDIRECT_URIS` add a preconfigured public native client; omit both for dynamic registration.

## Routing and authorization

The issuer is `${PUBLIC_ORIGIN}/dot-feishu/oauth`; resource `${PUBLIC_ORIGIN}/dot-feishu/mcp`. Register `${PUBLIC_ORIGIN}/dot-feishu/auth/feishu/callback` in the Feishu application's login settings. Expose `/dot-feishu/*`, `/.well-known/oauth-authorization-server/dot-feishu/oauth` and `/.well-known/oauth-protected-resource/dot-feishu/mcp` through HTTPS without rewriting paths. Existing domain-root discovery routes are independent.

Dynamic registration at `/dot-feishu/oauth/register` accepts only public clients with authorization-code/refresh grants and the exact callback `https://chatgpt.com/connector_platform_oauth_redirect` or `https://chatgpt.com/connector/oauth/[A-Za-z0-9_-]+`. PKCE S256 is required. New registration is closed by default. Set `DCR_REGISTRATION_UNTIL` to a future UTC ISO timestamp (ending in `Z`) only while pairing a new client; use the setup workflow to open a short window (normally 24 hours). Restart the authorization process after changing its environment. Missing or expired windows return `registration_closed` without affecting existing client login or refresh. Registration uses an atomic 100-client cap, ten successful registrations per minute and twenty attempts per minute per process. Unused registrations expire after one hour and are purged before checking the cap, so anonymous clients cannot permanently consume all slots. Saving an owner-approved grant makes its linked client persistent; approved clients survive registration-window closure and continue refreshing normally. Registration cannot supply secrets or remote metadata URLs. Client registration and discovery do not authorize any account data.

`feishu:read` and `mail:read` are separate permissions. Mail consent covers mailbox headers and new-mail monitoring events, excluding bodies and attachments. Existing Feishu-only access/refresh tokens never gain mail permission automatically. Request a new authorization including `mail:read` to enable mail; request both scopes if both services are needed. No grant/database reset is required. Refresh requests cannot add scopes. Access tokens are opaque, expire after ten minutes and are checked against the live grant store. Refresh tokens rotate; reuse revokes the grant. Grants expire after seven days.

The proxy removes caller-supplied authorization, cookies, internal keys, scope and forwarded headers, then supplies `X-Connector-Key` and `X-Connector-Scopes` (a JSON array containing only the token's actual scopes intersected with owner permissions). The backend must reject missing internal keys and enforce scopes on each data/tool/event operation. Public health returns only `{ "ok": true }` and describes the auth process, not upstream data readiness.

SQLite records use mandatory AES-256-GCM payload encryption with record-bound authenticated data. Credential-bearing IDs and lookup indexes use HMAC-SHA256 with a separate derived subkey. Store the encryption key separately from the database and retain it across restarts. Wrong keys or storage modes fail closed; there is no plaintext fallback or migration. An operator can remove access by disabling the service or revoking/rotating this instance's grants; upstream Feishu account status is not checked on each MCP call after sign-in.

Tests cover owner isolation, DCR window/expiry/cap recovery and approved-client persistence, encrypted persistence/no plaintext credentials, explicit Feishu/mail consent, trustworthy proxy scopes, refresh non-escalation and replay revocation. Real application login, client compatibility, production TLS cookies and backend scope enforcement require deployment integration checks.
