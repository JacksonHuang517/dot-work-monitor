# 分层排障

先区分五层：**入口 → 采集授权 → MCP 登录与权限 → 真实订阅 → 平台通知**。一次只修复有证据出错的一层，保留数据库、密钥和 CLI 凭证。

| 现象 | 优先检查 | 下一步 |
| --- | --- | --- |
| HTTPS / health 不通 | DNS A/AAAA、证书、80/443、Caddy 状态 | `docker compose ps`；检查 Caddy 日志与入口占用 |
| health 成功，最近采集失败 | CLI 用户授权、邮箱登录、应用权限与出口网络 | 查对应的 `feishu_status` 或 `mail_status` |
| 飞书网页登录后被拒绝 | app ID、租户、当前用户 Open ID、应用可用范围、精确回调 | 使用配置的所有者账号；确认标识来自同一应用 |
| CLI 已登录，ChatGPT 仍要求登录 | 这是独立的 MCP OAuth 连接 | 在插件管理页完成 MCP 所有者登录 |
| MCP 登录成功但飞书采集失败 | 这是独立的 CLI 采集授权 | 在容器中完成 CLI 设备码流程 |
| 工具有飞书，没有邮箱 | `MAIL_ENABLED`、邮箱配置与 `mail:read` | 启用邮箱后重建/启动服务，重新授权并重新扫描 |
| 加邮箱后飞书工具消失 | 新授权是否仅请求了 `mail:read` | 重新申请 `feishu:read mail:read`，保留原库和密钥 |
| 工具正常，事件目录缺失 | 插件旧元数据、scope、平台账户能力 | 用户在插件详情页刷新/重新扫描；Dot 无法自行点击该操作 |
| 事件可见，订阅数为零 | Dot 是否真正调用 `events/subscribe` | 明确要求分别订阅飞书和邮箱事件，查看真实结果 |
| 有订阅，没有回调 | 是否匹配 kinds、有无新事件、初始基线、回调验证/网络错误 | 按下面的链路检查，不要以“连接成功”代替订阅成功 |
| 回调成功，Dot 没有提醒 | 平台后续异步处理、会话、通知条件/批处理规则 | 对照真实事件与 Dot 行为，检查账户界面；不能认定服务端已完成最终验收 |

## 飞书登录失效或续期失败

应用权限被撤销、用户撤销授权、CLI 凭证丢失或企业策略变化，均可能中断采集。按[部署指南的采集授权](deployment.md#5-完成飞书采集授权)重新完成设备码流程，并保留持久化数据卷。重建容器后反复需要登录，应先检查 CLI HOME 的卷是否仍挂载。

ChatGPT MCP 的 access token、refresh token 与 CLI 的用户令牌不是同一组。MCP 刷新失败应从插件管理页重新连接，CLI 失效则在容器终端重新登录。不要交换两边令牌，也不要复制浏览器 cookie 作为解决办法。

授权 scope 会保留原先授予的范围，刷新不会增加权限。增开邮箱后需要重新同意两个 scope，而不是让旧 refresh token 自动升级。改变所有者身份时，停用实例并撤销旧授权；只改配置不代表旧访问立即在上游失效。

## 消息搜索结果不完整

默认是当前用户授权范围内的全局时间搜索，受飞书索引更新延迟影响，并非直接订阅飞书消息推送。15 分钟重叠窗口减轻短暂延迟，但无法保证找到所有晚入索引的消息。故障恢复最多向前补查 24 小时。更早消息、撤回记录或超出授权范围的群无法保证覆盖。

先核对消息时间和当前授权用户，再比较状态的最近成功时间与覆盖字段。不要因为某条消息未命中就扩大成无限历史扫描；这会增加隐私、限流与漏页风险。

## 没有回调或回调校验失败

按顺序确认：

1. 事件目录中存在正确名称，活动订阅不为零，并且 kinds 匹配。`mail.attention` 的 kinds 是 `mail` / `health`；飞书的是 `message` / `task` / `calendar` / `health`。
2. 订阅的回调由平台实际提供，验证挑战成功；没有靠自建假地址模拟 Dot 订阅。
3. 测试数据产生在首轮基线之后。历史新增默认被抑制；已有内容没有变化时不会每轮重复发送。
4. 服务器允许 HTTPS 出站；DNS 能解析平台回调地址，时钟准确，TLS 证书链可验证。
5. 回调目标解析为公网地址。项目会拒绝私网、回环及其他非公网地址，且不跟随重定向；不要通过关闭校验绕过。若 DNS 污染或代理返回私网地址，修复网络解析。
6. 查看最近投递状态及错误。2xx 表示平台接收，后续通知仍是异步的。410 会停止该订阅，413 或其他不可重试错误需要修正原因；临时错误有有限重试，不是无限保留。

订阅可能到期或被平台取消，需要由平台续订/重新订阅；本项目不能自行创造平台回调。请同时检查 Dot 所在会话和平台通知条件。

## 邮箱认证、超限与覆盖

确认企业允许 IMAP，服务器允许出站 993，并使用企业要求的登录凭证。不同企业可能要求客户端授权密码或额外策略；本项目不承诺所有个人账户和邮箱服务通用。

只读 `INBOX` 的窗口按 UTC 日期搜索，名义回看 48 小时，日期取整使实际范围约 48–72 小时。每次最多 500 个头部；超过限制会使该轮失败并报告健康问题，不会悄悄截断后宣称完整覆盖。超大头部、连接超时或异常 IMAP 响应也会使该轮失败。

不要把邮箱密码改写到命令参数或共享 `.env` 中；通过受保护的本地凭证文件更新并重启。邮件正文和附件不在本项目的排障读取范围内。

## 时间偏移与服务器时区

服务器和容器时钟应同步，使用 UTC 处理窗口、签名及每日逾期去重。界面显示本地时间时，先换算成同一时区再比较。CLI 子进程按 UTC 解释自己的格式化时间，不应根据宿主机时区猜测。

API 原始 ISO 时间戳需要明确时区。缺少时区的任意字符串不能按本机时区静默转换；只有代码显式处理的 CLI 时间格式有固定 UTC 约定。消息搜索参数使用整数秒时间，飞书可能拒绝小数秒。修改解析时重跑 `tests/test_source.py`，保留相关时区与格式回归样例。

## 数据库或密钥不匹配

先停止写入并保留备份。恢复与当前数据库配套的原密钥；不要把“重新生成密钥”当成解密失败的修复。缺少原密钥的密文无法可靠恢复。新实例应使用新密钥和新状态目录，旧实例恢复则必须成套恢复。

## 提交问题前

提供版本/提交号、部署方式、出错层、发生时间（注明时区）、状态字段和脱敏错误类别。说明是否完成真实订阅、是否收到回调 2xx、Dot 是否出现通知。不要上传数据库、授权 URL、设备码、cookie、令牌、私钥、密码或真实消息/邮件头。

### registration_closed

这是新客户端注册窗口已关闭，既有连接仍可刷新。由所有者运行 `.venv/bin/python scripts/setup.py --open-registration-hours 24` 并重启 monitor 后重新添加连接。不要删除授权库或重新生成密钥。
